# 📚 책장 (BOOKSHELF)

읽고 싶은 책을 관리하고, 독서 기록을 남기며, 현재의 기분과 관심사에 맞는 책을 AI에게 추천받는 개인 독서 웹서비스입니다.

## 주요 기능

- **나의 책**: 책 추가, 읽기 상태(읽고 싶은 책 / 읽는 중 / 읽은 책) 변경, 삭제
- **AI 책 추천**: 자유로운 사용자 입력을 Gemini API에 전달해 실제 출간 도서 한 권과 추천 이유 출력
- **독서 기록**: 별점, 한줄평, 기억하고 싶은 문장, 나에게 남은 것을 저장·삭제
- **로컬 저장**: 책과 독서 기록은 브라우저 `localStorage`에 저장
- **반응형 UI**: 데스크톱과 모바일 화면 대응
- **실패 처리**: 빈 입력, 로딩 상태, HTTP/API 오류 메시지 처리


## 로컬 실행

### 1. 저장소 준비

```bash
git clone <https://github.com/Chaewon81/A1-3-bookshelf.git>
cd <A1-3-bookshelf>
```

### 2. Python 의존성 설치

```bash
pip install -r requirements.txt
```

### 3. 환경변수 설정

프로젝트 루트에 `.env` 파일을 만들고 다음 값을 설정합니다.

```text
GEMINI_API_KEY=your_api_key_here
```

> `.env`, `.env.local`은 `.gitignore`에 포함되어 있으며 GitHub에 업로드하지 않습니다. 실제 API Key는 README나 스크린샷에도 노출하지 않습니다.

### 4. Vercel CLI로 로컬 실행

```bash
vercel dev
```

터미널에 표시되는 로컬 주소(기본 `http://localhost:3000`)에서 확인합니다. Live Server는 정적 프론트엔드만 실행하므로 Python `/api` 테스트에는 `vercel dev`를 사용합니다.

## AI 입력 / 출력 / 실패 처리

**입력**: 사용자가 현재 기분, 관심 분야, 원하는 책의 분위기 등을 자유롭게 작성합니다.

**출력**: Gemini가 실제 출간 도서 한 권을 `title`, `author`, `reason` JSON 형식으로 반환하고 프론트엔드가 카드 형태로 표시합니다.

**실패 처리**:
- 빈 입력 → 입력 안내 메시지
- 요청 중 → 로딩 메시지 + 추천 버튼 비활성화
- HTTP/API 오류 → “추천을 불러오지 못했습니다. 잠시 후 다시 시도해주세요.” 표시

## Troubleshooting / 개발 중 해결한 문제

### Live Server와 Python API
Live Server에서는 정적 HTML/CSS/JS는 확인할 수 있지만 Vercel Python Serverless Function은 실행되지 않았습니다. 전체 기능 테스트는 `vercel dev`로 전환했습니다.

### Gemini 503 High Demand
개발 중 `gemini-3.7-flash` 호출에서 `503 UNAVAILABLE` / high demand 오류를 경험했습니다. 외부 AI API는 일시적인 과부하나 가용성 문제가 생길 수 있음을 확인했고, 사용자에게 재시도 메시지를 제공하도록 오류 처리를 추가했습니다. 개발 과정에서는 더 가벼운 모델로 변경해 테스트를 이어갔습니다.

### Vercel Python 의존성 / uv 환경
새 PC에서 Vercel Python builder가 사용하는 의존성과 `uv`/PATH 문제를 확인하고 환경을 정리해 `vercel dev` 실행을 복구했습니다. Python 패키지는 `requirements.txt`로 명시해 재현 가능하도록 했습니다.

## AI 기능 테스트 사례

AI 책 추천 기능은 정상 입력뿐만 아니라 빈 입력과 비교적 긴 입력에 대해서도 동작을 확인했습니다.

### 1. 정상 입력

**입력 예시**

```text
요즘 진로를 고민하고 있어요. 너무 무겁지 않으면서 생각할 거리를 주는 한국 소설을 읽고 싶어요.
```

**결과**

- `/api/recommend`로 입력값이 전달됩니다.
- Gemini API가 책을 추천합니다.
- 책 제목, 저자, 추천 이유가 화면에 표시됩니다.

**정상 응답 형식**

```json
{
  "title": "책 제목",
  "author": "저자",
  "reason": "추천 이유"
}
```


### 2. 빈 입력

**입력**

```text
입력값 없음
```

**결과**

API를 호출하지 않고 다음 안내 메시지를 화면에 표시합니다.

```text
추천받을 조건을 입력해주세요.
```

이를 통해 불필요한 AI API 호출을 방지합니다.


### 3. 긴 입력

**입력 예시**

```text
최근 진로와 앞으로의 삶에 대해 고민이 많습니다. 너무 무거운 자기계발서보다는 이야기 속에서 자연스럽게 생각할 거리를 얻고 싶습니다. 인간관계와 성장, 새로운 시작을 다루면서도 읽기 어렵지 않은 책이면 좋겠습니다. 한국 소설이나 번역 소설 모두 괜찮으며 현재 상황에서 부담 없이 읽으면서 앞으로의 삶에 대해 생각해 볼 수 있는 책 한 권을 추천받고 싶습니다.
```

**결과**

- 긴 문자열도 하나의 사용자 입력값으로 서버에 전달됩니다.
- Gemini가 입력 내용의 주요 조건을 바탕으로 책을 추천합니다.
- 정상 입력과 동일하게 책 제목, 저자, 추천 이유를 화면에 표시합니다.

## HTML / CSS / JavaScript 역할

이 프로젝트에서는 각 프론트엔드 기술의 역할을 다음과 같이 분리했습니다.

- **HTML**: 서비스의 구조를 담당합니다. 나의 책, AI 책 추천, 독서 기록의 세 섹션과 입력창, 버튼, 목록 등 화면을 구성하는 요소를 정의합니다.
- **CSS**: 화면의 디자인과 반응형 처리를 담당합니다. 카드 형태의 레이아웃, 간격, 버튼과 입력창 스타일을 지정하고 `@media` 미디어쿼리를 사용하여 모바일 화면에서도 자연스럽게 표시되도록 합니다.
- **JavaScript**: 사용자의 행동과 데이터 처리를 담당합니다. 책 추가·삭제·상태 변경, `localStorage` 저장, 독서 기록 관리, 버튼 클릭 이벤트 처리와 `fetch('/api/recommend')`를 통한 서버리스 API 호출 및 결과 표시를 수행합니다.

즉, **HTML은 구조, CSS는 표현, JavaScript는 동작**을 담당하도록 역할을 구분했습니다.


## AI 모델 및 성능·비용 고려

개발 과정에서 Gemini 모델을 이용했습니다. 처음 사용한 모델에서 `503 UNAVAILABLE / high demand` 오류가 발생하여 상대적으로 가벼운 모델로 변경해 테스트를 진행했습니다.

AI 기능의 속도와 비용을 개선할 수 있는 방법은 다음과 같습니다.

| 방법 | 장점 | 고려사항 |
| --- | --- | --- |
| 경량 모델 사용 | 응답 속도가 빠르고 일반적으로 비용 부담이 낮음 | 복잡한 추론 품질이 낮아질 수 있음 |
| 요청 결과 캐싱 | 동일하거나 유사한 요청의 API 호출 횟수를 줄일 수 있음 | 사용자별 맞춤 추천에서는 캐시 활용 범위가 제한적임 |
| Timeout 설정 | API 지연 시 사용자가 계속 기다리는 문제를 방지 | 너무 짧으면 정상 요청도 실패 처리될 수 있음 |
| 호출 횟수 제한 | API 비용 및 쿼터 초과 위험 감소 | 사용자의 이용 횟수가 제한될 수 있음 |

현재 서비스는 학습용 소규모 프로젝트이므로 복잡한 캐싱 시스템은 적용하지 않았으며, **경량 모델 사용과 오류 안내 처리**를 적용했습니다.

실제 서비스로 확장한다면 호출량 모니터링, 캐싱, Timeout, 사용자별 호출 횟수 제한 등을 함께 고려할 수 있습니다.


## API Key 유출 대응 절차

API Key는 프론트엔드 코드에 작성하지 않고 **Vercel Environment Variables**에서 관리합니다.

만약 API Key가 GitHub, 로그, 스크린샷 등에 노출된 경우에는 다음 순서로 대응합니다.

1. 노출된 API Key를 즉시 폐기(Revoke)합니다.
2. 새로운 API Key를 발급합니다.
3. Vercel Environment Variables의 Key를 새 값으로 교체합니다.
4. Production을 다시 배포하고 정상 작동 여부를 확인합니다.
5. GitHub commit history, 로그, 스크린샷 등을 확인하여 기존 Key가 남아 있는지 조사합니다.
6. API 사용량과 로그를 확인해 비정상적인 호출이나 비용 발생 여부를 점검합니다.

API Key는 **README, JavaScript, Git 저장소에 저장하지 않는 것**을 기본 원칙으로 합니다.


## 프레임워크를 사용하지 않은 이유와 도입 시 영향

이번 과제에서는 요구사항에 따라 React나 Vue 같은 프레임워크를 사용하지 않고 **Vanilla HTML/CSS/JavaScript**로 구현했습니다.

이를 통해 DOM 조작, 이벤트 처리, `fetch`, `localStorage` 등 웹의 기본 동작을 직접 이해하는 데 집중할 수 있었습니다.

### Vanilla JavaScript의 장점

- 프로젝트 규모가 작을 때 구조가 단순합니다.
- 별도의 복잡한 빌드 환경이 필요하지 않습니다.
- HTML, CSS, JavaScript의 기본 동작을 직접 학습할 수 있습니다.

### Vanilla JavaScript의 단점

- 기능과 화면이 많아지면 DOM 처리 코드가 복잡해질 수 있습니다.
- 여러 화면에서 데이터를 공유해야 할 경우 상태 관리가 어려워질 수 있습니다.
- 프로젝트 규모가 커질수록 코드 유지보수가 어려워질 수 있습니다.

### React 또는 Vue 도입 시 예상되는 변화

향후 React 또는 Vue 같은 프레임워크를 도입한다면 다음과 같은 변화가 예상됩니다.

- 책 카드, AI 추천 결과, 독서 기록 등을 **컴포넌트 단위**로 분리할 수 있습니다.
- 화면 상태와 데이터를 보다 체계적으로 관리할 수 있습니다.
- 반복되는 UI를 재사용하기 쉬워집니다.
- 현재의 `index.html`과 `js/app.js` 중심 구조를 컴포넌트 기반 구조로 재작성해야 합니다.
- npm 등의 패키지 관리와 빌드 환경이 추가로 필요합니다.

따라서 현재와 같은 소규모 학습 프로젝트에는 Vanilla JavaScript가 단순하고 적합하지만, 서비스 규모와 기능이 커질 경우 React 또는 Vue 같은 프레임워크 도입을 고려할 수 있습니다.
